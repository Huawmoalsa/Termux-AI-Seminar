# Termux-AI Seminar

A multi-agent AI reasoning framework designed for constrained environments such as Android and Termux.

Termux-AI Seminar separates AI-generated proposals from decision authority, execution, evidence, and trust. Its purpose is to allow multiple AI agents to independently propose and develop solutions while keeping final decisions and system capabilities under explicit control.

## Core Seminar Protocol

The Seminar follows a controlled multi-stage process:

```text
PROPOSAL
    ↓
SELECTION
    ↓
INDEPENDENT_DEVELOPMENT
    ↓
UPGRADE_SELECTION
    ↓
DEVELOPMENT
    ↓
UPGRADE_SELECTION
    ↓
FINAL_DECISION
    ↓
EXECUTION
    ↓
EVIDENCE
    ↓
GUARD
    ↓
COMPLETED / FAILED
The Manager is the decision authority.
AI agents provide proposals and development work. Their responses are not treated as proof merely because they were generated by an AI model.
A selected developer is temporarily excluded from the immediately following upgrade round to encourage independent review. The developer may return in a later round.
Development is bounded by a maximum of three rounds, with early termination possible when further development produces no material improvement.

## Trust Model

The project treats trust as an explicit architectural boundary.

The basic model is:

```text
Tool
  ↓
Evidence Adapter
  ↓
Authenticated Evidence Ledger
  ↓
Trust / Proof Layer
AI-generated statements remain proposals or interpretations unless supported by an appropriate evidence path.
Execution output is not automatically considered trusted evidence.
The evidence ledger preserves provenance and historical evidence records. Historical records are not rewritten merely to remove obsolete runtime files from the current repository.
Agent Security Boundary
Seminar agents are intentionally separated from the legacy device-tool execution path.
The Seminar agent entry point uses:
allow_tools=False
This means Seminar agents do not receive the legacy tool definitions and do not enter the legacy tool-dispatch path through the Seminar LLM interface.
A model may still generate text resembling a tool call. Such text is not equivalent to actual device execution.
Execution is handled through an explicit execution boundary rather than through unrestricted LLM output

## Broadcast

The Seminar can use bounded multi-agent broadcast for proposal, verification, comparison, and analysis workflows.

Broadcast responses are treated as independent model outputs. They do not acquire decision authority merely by being produced by multiple agents.

Unavailable or unreliable providers can be skipped, allowing the system to continue with available agents or local fallback behavior.

Running the Seminar
The package can be invoked with:
PYTHONPATH=src python -m seminar --help
The interface currently provides deterministic local operation and an LLM-backed mode.
LLM mode can be invoked with:
PYTHONPATH=src python -m seminar --llm "Your task here"
Provider availability depends on the configured models, credentials, network connectivity, and provider-side limits.
Execution Model
The Seminar does not treat a candidate answer as an executable command.
A candidate passes through the Seminar decision process first. Explicit execution requires an appropriate execution plan and execution boundary.
This distinction is intentional:
LLM output
    ≠
Trusted evidence
    ≠
Executable instruction
The system therefore separates reasoning, decision-making, execution, evidence, and trust rather than allowing an LLM response to directly control the device.

## Design Principles

The project is built around several principles:

1. **LLMs are not truth authorities.**
2. **Proposals are not proof.**
3. **Execution is explicitly bounded.**
4. **Evidence requires provenance.**
5. **Trust is established outside ordinary model output.**
6. **The Manager controls Seminar decisions.**
7. **Independent agents are used to reduce single-response dependence.**
8. **Validation should distinguish structural correctness from live provider behavior.**
9. **Historical evidence should remain immutable.**
10. **Legacy capabilities should not become implicit Seminar capabilities.**

## Current Limitations

The project is still under active development.

In particular:

- Live LLM providers may fail because of authentication, rate limits, unavailable models, or network conditions.
- External-provider end-to-end behavior is not yet considered fully validated.
- Android/device execution remains explicitly separated from Seminar agent reasoning.
- Some legacy project components remain because other parts of the existing runtime still depend on them.
- The current repository represents the Seminar architecture and migration state; it is not a claim that every planned capability is production-ready.

## Security Position

The primary security objective of the current architecture is to prevent an LLM agent from obtaining implicit authority to execute arbitrary device operations.

A model response containing something such as:

```text
<tool_call>
pwd
</tool_call>
is still model-generated content unless an explicitly authorized execution path accepts and executes it.
Seminar agents are not granted that authority through the normal Seminar LLM interface.
Development
The project is being developed primarily in Termux on Android, with resource and connectivity constraints taken into account.
The architecture is intentionally modular so that reasoning, orchestration, LLM providers, execution, evidence, trust, and presentation can be validated independently.
